# Host metrics (daemon collector) — AGENTS.md

Fire-and-forget host-metrics collection (async `/proc` + `statfs` reads, **no** per-interval subprocesses) and scheduling, sent via `POST /api/daemon/v1/metrics`. The wire contract (`src/metrics/contract.ts`, `METRICS_SCHEMA_VERSION = 6`) groups every reading by **entity** — host, network device, filesystem, block device, GPU, hardware signal, ingress source, database proxy — instead of a flat key list. Every leaf metric is `number | null` (missing is always `null`, never coerced to `0`), and each entity carries a stable logical id instead of relying on positional/part membership. There is no `MetricPart`/allowlist concept anywhere in this contract: a family is either always present (the universal host-scoped groups) or presence-derived — an entity array holds however many the topology/adapter actually found this tick, empty when none did, never a placeholder. **No Analytics Engine concept (`doubleN`/`blobN`/positional slot/sentinel) appears anywhere in this repo** — this daemon only collects and emits `MetricsSample`; physical AE packing is entirely the instance's concern (`../turbopanel/src/daemon/metrics/backends/cloudflare/`).

Root context: `../../AGENTS.md`. Instance-side storage/query/caching: `../../../turbopanel/src/daemon/metrics/AGENTS.md`. Cross-repo `../<repo>/…` links are relative to the repo root.

## Topology (`topology/`)

Stable device/filesystem/GPU/hardware-signal/NUMA/CPU identity and generation tracking, discovery-only (no telemetry) — see `topology/topology.ts`'s doc comment for the composition shape (`collectTopology`, one `*-topology.ts` discovery module per entity kind run in parallel where independent). Two independent generation counters ride every sample's `metadata`:

- **`topologyGeneration`** (`topology/generation.ts`) bumps whenever the discovered entity set changes shape (a NIC added/removed, a filesystem (un)mounted, a GPU added/removed, etc.) — the instance-side query layer's replacement for v3's `hardwareProfileGeneration` (see `../turbopanel/src/daemon/metrics/query/cache.ts`).
- **`bootGeneration`** (`topology/boot-generation.ts`) bumps only on a host reboot (kernel boot id change) — the invalidation signal every `CounterBaselineTracker` delta/rate checks before diffing across two snapshots, so a reboot never produces one fabricated rate compressing the gap.

`hardwareSignals` is a conservative physical-only catalog — CPU package temperature/power, NVMe/`drivetemp` storage temperatures, trustworthily labeled board/inlet/DIMM/VRM/chipset temperatures, plus two synthetic CPU virtual signals (hottest-core temperature, thermal-throttled percent) and the **entity-joined** signals: one temperature / memory-temperature / power per topology-enumerated GPU (`gpuSignalId` → `signal:gpu:<gpuId>:<kind>`) and one temperature per topology-enumerated *service* block device that a disk-temperature probe actually backs (`blockTemperatureSignalId` → `signal:block:<deviceId>:temperature`). Operator-facing `label` rewrites kernel `Package id 0` / `package-0` to **CPU package temperature** / **CPU package power**; an hwmon-backed `signalId` stays `signal:${chip}:${kernelLabel}`, while the two entity-joined forms are resolved by **exact-id lookup only** — a `gpuId`/`deviceId` is opaque and may itself contain a `:`, so they are never split apart. This is why every physical reading in the contract rides one family behind one `isPhysicalMachine()` gate, one page order, and one `physicalHardwareSignalSlots` entitlement: GPU temperature/power and drive temperature used to be `GpuSample`/`BlockDeviceSample` fields, which put physical-only readings on entities a VM also reports. Entity signals are never fabricated — a GPU signal requires that GPU in topology (gated on topology alone, since NVIDIA exposes no hwmon chip to gate on), and a drive signal requires both `isServiceDevice` and a matching probe. Fan tachometers are never projected here: fan RPM has no telemetry family at all (fan *fault/alarm* detection still works, from the broader live candidate map — see **Events** below). Telemetry *reading* for topology-identified hardware signals is `collector/hardware-signals.ts` (`buildHardwareSignalSamples`): re-runs `discoverSensors` against the same `io`/`sysRoot` topology used, joins back to topology identity via the `signal:${chip}:${label}` id, and resolves temperature (instantaneous) and CPU RAPL power (tracked-rate `Δenergy_uj/Δseconds/1e6`, mirroring `cpuPowerFromEnergy`'s math as a `CounterBaselineTracker` key); the two synthetic CPU signals are computed directly (max live per-core temperature; cumulative `package_throttle_total_time_ms` tracked-rate, same convention as GPU `throttlePercent`); `component: "gpu"` signals resolve from the per-GPU merge `buildGpuSamples` already computed this tick (threaded in as `gpuThermals`, so there is no second device read and NVIDIA's hwmon-less GPUs still resolve), and `component: "drive"` signals resolve in a second phase from this tick's own `component: "disk"` probe readings via `buildBlockDeviceTemperatures`. Topology discovery therefore trails GPU/block discovery, and the collector tick runs `buildGpuSamples` before `buildHardwareSignalSamples`. A signal topology already identified but unreadable this tick stays present with `value: null` — never dropped. Control-plane persistence for reported generations is `../turbopanel/src/client/servers/server-topology-records.ts`. Physical-machine classification (bare metal vs. VM/hypervisor) lives in `topology/physical-classifier.ts`'s `isPhysicalMachine`, memoized once per process by `events/index.ts`'s `EventCollectorSet`. Vendors that ship both hypervisors and real hardware (`google`, `microsoft corporation`) require a corroborating `product_name` marker before a host is demoted to virtual — v4 substring-matched them on `sys_vendor` alone, which misclassified bare-metal boards from those vendors and silently discarded every hardware signal they reported, since a VM's `physicalHardwareSignalSlots` is 0. Operator sensor/NIC-slot overrides are a separate, still-live mechanism — `collector/sensors/overrides.ts`'s `HardwareProfile` JSON round trip (`<daemonStateDir>/metrics/hardware-profile.json`, pushed over `topology-overrides-update`) — orthogonal to topology identity; see **Sensor subsystem** below.

## Events (`collector/events/`)

`contract.ts`'s closed `MetricEventKind` catalog is populated by one stateful sub-collector per catalog area (`oom-kill.ts`, `hung-task.ts`, `conntrack.ts`, `filesystem-state.ts`, `mdstat.ts`, `edac.ts`, `smart.ts`, `nic-link.ts`, `fabric-state.ts`, `physical-health.ts`, `gpu-health.ts`, `clock-sync.ts`, `generation-events.ts`), each holding its own tick-to-tick dedupe/cooldown state and emitting only on a state *transition* — never every tick a condition holds. `events/index.ts`'s `EventCollectorSet` composes all of them: wraps each in its own try/catch (`safeAsync`) so one throwing never drops another's events, resolves physical-machine classification once per process and memoizes it, and truncates the combined result to `MAX_EVENTS_PER_DETECT_TICK` (128, mirroring `contract.ts`'s private `MAX_METRIC_EVENTS_PER_SAMPLE` — `buildMetricsSample` throws the *entire* sample away over that cap). `linux-collector.ts` calls it via the optional `CollectorDeps.eventCollectors` seam; absent (e.g. a test collector), `events` stays `[]`, matching every other adapter's absent-default convention. `fabric-state.ts` reads `instance/commands/fabric.ts`'s `getLastObservedFabricPeers()` — a cache stashed by `wg show tp0 dump` whenever an *instance-initiated* reconcile/path-probe already runs it — rather than spawning its own `wg` subprocess. `HARDWARE_HEALTH_EVENT_KIND` in `contract.ts` classifies every kind as a physical-hardware-health signal or not — the split the instance's `capability-plan.ts` (`../turbopanel/src/daemon/metrics/capability-plan.ts`) actually gates.

`smart.ts`'s `smartctl -H -j -n standby` (~10 min cadence, one per physical block device) is the collector's only remaining subprocess-per-tick exception, gated behind its own internal low-cadence timer, never the ~60 s metrics tick itself. `hung-task.ts` primarily reads `/dev/kmsg` — non-blocking (`O_NONBLOCK`) and cursor-based (tracks the last-consumed record `seq`), so a read either returns an already-buffered record or fails `EAGAIN` immediately, never blocking the collection tick the way a plain blocking open would; bounded `dmesg --level=err,warn -x` is a strictly secondary fallback for hosts where `/dev/kmsg` is unreadable (`kernel.dmesg_restrict=1` without `CAP_SYSLOG`), still gated behind the same ~2 min timer. `clock-sync.ts` reads `host/time-sync.ts`'s cached `getLastObservedTimeSync()` fact — populated as a side effect whenever some other real caller (e.g. idle presence) actually invokes `readTimeSync()` — rather than spawning `timedatectl` itself. `mounts.ts`'s `MountEntry` carries an `options` field (the fourth `/proc/mounts` column) for `filesystem-state.ts`'s ro/remount detection.

## Host metrics

Samples are sent via authenticated `POST /api/daemon/v1/metrics` (`DaemonApiClient.sendHostMetrics`, `src/instance/api-client.ts`, fire-and-forget). Every sample is one `MetricsSample` (`{ type: "metrics", metadata, host, networks, filesystems, blockDevices, gpus, hardwareSignals, ingressSources, databaseProxies, events, diagnostics?, router? }`), mirrored (not build-coupled) with the instance's own copy at `../turbopanel/src/daemon/metrics/contract.ts`. `metadata` carries `version` (`METRICS_SCHEMA_VERSION = 6`), `sampledAt`, `intervalSeconds`, `sequence`, `topologyGeneration`, and `bootGeneration`. v6 dropped the `collectionMode` (`"baseline"` / `"live"`) discriminator: a live lease changes the scheduler cadence, and the resulting `intervalSeconds` is the only thing any consumer ever needed to tell the two apart. `host` is the **universal baseline** — always present, five subsystem groups (`cpu`, `kernel`, `memory`, `storage`, `network`) covering the instance's `host.system`/`host.io` families — every field a scalar `number | null`, never entity-scoped. Everything else is either a **presence-derived array** (`networks`, `filesystems`, `blockDevices`, `gpus`, `hardwareSignals`, `ingressSources`, `databaseProxies` — however many the topology/adapter actually found this tick, `[]` when none) or one of the two **optional host-wide singletons**: `diagnostics?` (the merged depth family — present whenever the collector could read any of `/proc/stat`, `/proc/meminfo`, `/proc/vmstat`; in practice every Linux host) and `router?` (the shared hosting Traefik — present only on hosts actually running it). Both carry no entity id and are omitted entirely rather than sent all-`null`. v6 removed the never-populated `numaNodes` reserved family outright.

**This contract carries no per-core surface at all.** The live per-core family (`cpuCoreLive`) and the old `cpuDetail`'s four embedded busiest-core hotspots were both removed outright, not defaulted off, so a 64-core host costs exactly the same rows and the same storage as a 2-core one and no capability knob can change that. `host.cpu.saturatedCoreCount` (logical cores at or above 90% busy this interval — `collector/cpu.ts`'s `saturatedCoreCount`) is the host-scoped scalar that replaced v4's `maxCoreBusyPercent`: a maximum saturates as a statistic once a box has many cores, whereas a count reads 0 on a healthy host, 1 when a single thread is wedged, and large when the machine is genuinely loaded.

**Scheduling** (`src/metrics/scheduler.ts`): `MetricsScheduler` takes an injected `MetricsSink` (`attach(send)`) rather than the raw `WebSocket` — the WS keeps only commands/outbox + the cell ping. On attach (first registration and every reconnect, including the co-located self-hosted daemon) the first sample POSTs immediately so gauges (load / memory / disk / uptime) populate without waiting. A primed second sample **2 s** later (`METRICS_PRIME_MS`) plus deterministic per-`serverId` phase jitter ≤**5 s** (`METRICS_JITTER_MAX_MS`, FNV‑1a) fills CPU / disk / net rates (two-snapshot deltas). Steady cadence is then one sample ~every **60 s** (`METRICS_INTERVAL_MS`); jitter does not change query resolution. Live sessions switch cadence to **10 s** (`LIVE_METRICS_INTERVAL_MS`, `live-leases.ts`) while at least one lease is active. Monotonic process-local `sequence` resets on daemon restart (not persisted). Fire-and-forget, disposable — no acks, retries, or outbox. Never blocks startup, connect, liveness, command dispatch, shutdown, or reconnect. Factory/collect/send failures are rate-limited (`METRICS_LOG_RATE_LIMIT_MS` = 5 min) and must not tear down the socket. Overlapping ticks are dropped; the steady interval arms when the primed tick fires (not after first-collect completion). Attach-scoped generation ignores stale in-flight emits across detach/reconnect. Scheduler rebinding tracks `#metricsSchedulerServerId` separately from `#tokenServerId` so jitter stays tied to the authenticated server after identity recovery.

**Collector** (`src/metrics/collector/`): async reads only — **no subprocesses per interval** (no `top`/`vmstat`/`iostat`/`free`/`df`/`ps`/`sar`; the Docker data-root query goes over the Engine API Unix socket, is cached after success, and bounds failure re-probes to `DOCKER_DATA_ROOT_RETRY_MS`). `smart.ts` is the only events sub-collector that spawns a real subprocess, on its own internal low-cadence timer, never the metrics tick itself — `hung-task.ts` reads `/dev/kmsg` (falling back to a bounded `dmesg` on the same low-cadence timer only when kmsg is unreadable) and `clock-sync.ts` reads a cached fact rather than spawning anything itself (see **Events** above). `linux-collector.ts` orchestrates one tick: composes the `TopologySnapshot` (identity + both generations), the shared counter-baseline layer (`baseline.ts`'s `CounterBaselineTracker` — first-sample and counter-decrease/reboot both null a rate, never fabricate one across the gap), and every per-domain parser/builder module, then hands the result to `buildMetricsSample` (`contract.ts`), which sanitizes/clamps every leaf and enforces the events-per-sample cap. Process count (`host.cpu.processCount`) is `CollectorDeps.countProcesses` (production: `countProcessesInProc`); host-free scheduler tests stub it because FakeClock only drains microtasks and cannot wait on a live `/proc` PID scan.

Sources: `/proc/stat` (aggregate + per-core CPU jiffies, `procs_running`/`procs_blocked`), numeric `/proc` PID directories (`host.cpu.processCount` — total processes, distinct from the run-queue gauges), `/proc/pressure/{cpu,memory,io}` (PSI `some`/`full` percentages), `/proc/loadavg`, `/proc/meminfo` (raw bytes only, swap-absent hosts report `null` never `0`; `host.memory.usedBytes` is `MemTotal - MemAvailable` and `cachedFilesBytes` is `Cached + Buffers + SReclaimable - Shmem` — `Shmem` is subtracted because tmpfs pages sit inside `Cached` but are not reclaimable file cache), `/proc/vmstat` (reclaim/compaction rates), `/proc/uptime`, `/proc/diskstats` (throughput, IOPS, `Δticks/Δops` read/write latency, `Δio_ticks` utilisation and `Δtime_in_queue` average queue depth, keyed by topology `deviceId`), `/proc/net/dev` plus `/sys/class/net/<name>/statistics/*` (preferred per-NIC directional counters, falling back to `/proc/net/dev` when a device has no sysfs `statistics/` directory), `/proc/net/{netstat,snmp}` (TCP retransmit percent), `/proc/net/softnet_stat` (softnet drops), `/proc/sys/fs/{file-nr,file-max}` and `/proc/sys/net/netfilter/nf_conntrack_{count,max}` (kernel-limit used-percentages), `/proc/sys/kernel/osrelease`. **Three storage probes** via `node:fs/promises` `statfs` (no `df`; Deno needs `--allow-sys=statfs` in addition to `--allow-read` — granted on `turbopaneld.service` source-mode ExecStart, `deno.json` `start`/`dev`/`compile*`): system `/`, the hosting path (admin override from `<daemonStateDir>/metrics/hardware-profile.json`, else `principalHomeRoot` — `collector/hosting.ts`), and the Docker data root (Docker Engine API `GET /info` `DockerRootDir` via `src/docker/client.ts`, `null` when Docker is absent) — raw bytes normalized first (`totalBytes = blocks * bsize`, `availableBytes = bavail * bsize`), no percent reduction. The hosting path walks up to the nearest existing ancestor directory (bounded at `/`) before being probed — `principalHomeRoot` is only created on first tenant principal, and an admin override can name a not-yet-provisioned filesystem, so `resolveHostingPath` never hands `statfs` a path guaranteed to fail.

**Network topology** (`topology/network-topology.ts` + `topology/network-classifier.ts` + `collector/network.ts`): every interface enumerated from `/proc/net/dev` is classified from name prefixes first (`classifyInterface`: `loopback` / `container-bridge` (`veth*`/`docker*`/`br-*`/`virbr*`/`vnet*`/`tap*`/`tun*`) / `fabric` (TurboFabric names, seeded `tp0`; registration wins over a prefix match)) and then, for everything else, from sysfs (`network-classifier.ts`): a hardware-backed NIC (`device/uevent` readable — PCI/USB/virtio/Xen/Hyper-V) or the *topmost* bond/bridge/team aggregate stacked on one (`lower_*` links, `bonding/`/`bridge/` dirs, `DEVTYPE`) is an **`uplink`**; every physical-backed device under such an aggregate (bond ports, bridge members, a bond nested under a bridge) is a **`member`**; a present plain-Ethernet device with no bus device, no `DEVTYPE`, no `lower_*` and no container prefix (a container's renamed veth peer — the LXC/Proxmox-CT/veth-VPS `eth0`, the only link that host has) is also an **`uplink`**; VLAN/macvlan children of an uplink, tunnels (WireGuard/vxlan/tun — `DEVTYPE` or non-Ethernet ARPHRD `type`), and other software devices are **`virtual`**. `eth0:1`-style IP aliases are not devices and never appear. Only `uplink`s are monitorable NIC slots. Each device is stamped with stable identity (`identity.ts` — hardware-backed devices by MAC, preferring `bonding_slave/perm_hwaddr` so active-backup bond ports sharing the bond MAC stay distinct, else PCI slot; software devices hash name+driver, never MAC, so a bond/VLAN/bridge stack sharing one MAC never collapses onto one id — except the bare-Ethernet container `eth0` above, which has no stack and keeps its `mac:` id) plus `speed`/`mtu`, and the one uplink carrying the host's default route (`/proc/net/route`, IPv6 fallback; resolved through VLAN children and members down/up to the uplink) carries `defaultRoute: true`. `topology/slot-mapping.ts` turns that into `SlotMapping.normalNicSlots` (array, slot 1 first, `MAX_NIC_SLOTS` = 11 — the S7 / SX entitlement): the operator's `nicSlotDeviceIds` list wins outright, otherwise exactly the default-route uplink (first sorted uplink as fallback). `linux-collector.ts` samples **only** `normalNicSlots` (slot order) plus fabric devices — members/virtual/container-bridge/loopback are enumerated for identity and the settings picker but never emitted — via `collector/network.ts`'s `buildNetworkDeviceSamples`, one `NetworkDeviceSample` per monitored device keyed by the stable `deviceId`, so a kernel rename between ticks never fabricates a rate. Reads per-NIC directional counters via `/sys/class/net/<name>/statistics/*`, falling back to `/proc/net/dev` when unavailable. The control plane mirrors `types.ts`/`slot-mapping.ts` (`../../../turbopanel/src/client/servers/topology-{types,slot-mapping}.ts`) and enforces the per-server slot count (`capability-plan.ts`'s `normalNicSlots`: 2 hosted, 11 self-hosted) at ingest.

**Sensor subsystem** (`sensors/`): hwmon/thermal-zone temperatures, RAPL energy-delta CPU power, hwmon `power1_average` GPU power, NVMe/`drivetemp` disk temperatures, hwmon `fanN_input` tachometers (CPU/system/GPU-attributed by chip), and GPU utilization: AMD `gpu_busy_percent` (instantaneous gauge) plus Intel i915/Xe DRM `engine/*/busy` accumulating nanosecond counters when that file exists (two-snapshot delta, busiest engine, same first-sample/`boot_id` nulling as RAPL CPU power). Stock i915 (Debian 6.12, current Alpine) does **not** ship `engine/*/busy` — `btop` / `intel_gpu_top` read engine busy and RAPL `energy-gpu` via `perf_event_open` (needs `CAP_PERFMON` or root). The daemon does not take that capability: Intel iGPU utilization falls through to inverted `gt/gtN/rc6_residency_ms` (GT-awake percent, world-readable sysfs), and Intel iGPU watts fall through to RAPL PP1 `uncore`/`gpu` `energy_uj` under `/sys/class/powercap` (the sysfs twin of `energy-gpu`, same first-sample nulling as CPU RAPL). Kernel `energy_uj` is **0400** (root-only); the `rapl-access` Ansible role grants the daemon group `g+r` on install/converge (udev for reboot) so the collector can read it without `CAP_PERFMON`. Intel Alder Lake-N / Twin Lake (N150, PCI `8086:46D4`) typically **does not** register an `i915` hwmon chip, so GPU temperature and `power1_average` stay `null` — CPU package temp (`coretemp`) is the closest thermal; iGPU `memoryUsedBytes` stays `null` (`mem_info_vram_used` is AMD). NVIDIA GPU power/utilization ride the GPU adapter stack instead (see below — `nvidia-smi` would be a per-interval subprocess, so sysfs/NVML/DCGM are used instead). Admin overrides resolved from the operator-pushed `HardwareProfile` (`sensors/overrides.ts`, `<daemonStateDir>/metrics/hardware-profile.json`) beat auto-detection; the same file also carries the legacy `nic1`/`nic2` interface-name fields (no longer consumed) and the topology-identity pins (`nicSlotDeviceIds` — the monitored-NIC list, slot order — and `hostingFilesystemId`). Resolved sensor identities (`chip:label`) are daemon-internal only — never re-added to the wire sample. CPU % and per-second rates use two-snapshot deltas; first-sample rate metrics are **`null`** (never coerced to `0`), and a boot-generation change nulls rates, CPU, RAPL power, Intel DRM engine-busy GPU utilization, Intel RC6 utilization, and Intel RAPL GPU power — AMD `gpu_busy_percent` and fan RPM are point-in-time gauges, so the boot reset never touches them. GPU sensor selection is device-first (`selectGpuDevice`): candidates group per hwmon (or DRM card) device and one GPU feeds temperature, power, utilization, and fan — a multi-GPU host never mixes two cards in one reading. Intel iGPUs without an `i915` hwmon still appear as a GPU device when DRM `engine/*/busy` counters **or** RC6 residency exist. The `drivetemp` kernel module is opt-in (`sensors/drivetemp.ts`, `HardwareProfile.drivetempEnabled`): a push over `topology-overrides-update` that flips it false/unset → true fires a fire-and-forget `modprobe drivetemp` plus a `modules-load.d` drop-in for reboot durability; later pushes with the flag already `true` are a no-op. `drivetemp` exposes no `tempN_label`, so a SATA disk's label falls back to the raw attribute name (`temp1`) — the operator-facing rewrite happens client-side.

**Capability discovery** (`collector/capabilities.ts`): `collectMetricsCapabilities` is the on-demand payload behind `metrics-capabilities-request` — sensor candidate pools with live readings (`readTemperatureValue` / `readFanValue` / `readGpuPowerValue`; RAPL CPU power and GPU utilization stay `reading: null` because they are deltas), shared ambient/disk/system-fan pools, hosting/Docker `statfs` probes with `path_not_found` / `docker_absent` / `statfs_unsupported` reasons, name-prefix NIC classification, and a `/proc` process-count probe. Not part of the 60 s sample. The control plane's `GET /servers/:id/metrics/capabilities` waits on that correlated round trip.

When a disk hwmon's backing block device cannot be resolved, the chip name falls back to `<chip>@<hwmonDir>` (e.g. `nvme@hwmon3`) rather than the bare literal `nvme`. v4 used the literal, so two unresolvable NVMe drives both produced `signal:nvme:Composite` and one silently shadowed the other in the id map — losing a whole drive's temperatures on exactly the two-drive hosts v5 supports by default.

**GPU adapter stack** (`collector/gpu/`): `gpu/index.ts`'s `buildGpuSamples` merges up to three independent adapters per topology-identified GPU, in precedence order — **DCGM** (`dcgm-adapter.ts`, scrapes `dcgm-exporter`'s Prometheus endpoint, `DCGM_EXPORTER_ADDR`, the richest source when present), **NVML** (`nvml-adapter.ts`, direct FFI into `libnvidia-ml.so.1` — construction-time singleton, never re-`dlopen`ed), and **sysfs/DRM** (`sysfs-adapter.ts`, the universal fallback reading `/sys/class/drm/` and hwmon, covering AMD/Intel and NVIDIA hosts with no driver userspace installed). A field DCGM or NVML don't supply falls through to sysfs rather than the whole GPU sample failing; a host with none of the three adapters available for a topology-identified GPU still reports the entity with every field `null`. The adapters still read temperature/memory-temperature/power (they are its only source), but those are **not** `GpuSample` fields: `buildGpuSamples` merges them under the same per-field precedence and returns them separately as `GpuSamplesResult.thermals`, which feeds the `hardware.physical` signals above. `GpuSample` itself is workload telemetry only (utilization, memory, PCIe, throttle) — 6 fields, which is also what shrinks the instance's `gpu` AE row from 2 to 3 GPUs per page. `events/gpu-health.ts`'s `gpu_thermal_critical` reads `EventDetectContext.gpuThermals` — the adapter merge itself, deliberately **not** the resulting signals, which are `[]` on a GPU-passthrough VM.

**Block-device detail** (`collector/block-devices.ts` + `mounts.ts`): per-device diskstats samples (`buildBlockDeviceSamples`) and host-wide aggregates (`hostDiskAggregates`) are both scoped to topology-flagged `isServiceDevice === true` devices only (partitions and device-mapper layers excluded — I/O is accounted on the underlying physical device) and keyed by stable topology `deviceId`, never a positional index; sectors are 512 bytes per kernel convention. Two service devices are the v5 default floor (`detailedBlockDeviceSlots: 2`), matching the instance's 2-slot storage row.

Drive temperature is **not** a `BlockDeviceSample` field — it is a physical-only reading, so it rides `hardware.physical` keyed to the owning drive (`signal:block:<deviceId>:temperature`) and a VM, which emits no `hardware.physical` row at all, never carries a fabricated one. `buildBlockDeviceTemperatures` stays here as the join, but its caller is `collector/hardware-signals.ts` now, not `buildBlockDeviceSamples`: disk temperature probes arrive as `signal:<kernelName>:<label>`, and `sensors/discovery.ts` already resolves an NVMe or `drivetemp` hwmon chip down to its backing block device, which is exactly the name block topology uses. NVMe's `Composite` channel wins over the numbered internal probes — it is the vendor-computed whole-drive value the NVMe spec defines and the one the drive throttles on. Only `component: "disk"` readings are passed to the join; any other component's id parses into a meaningless kernel name that could shadow a real drive. The per-probe `disk` signals stay in the catalog alongside the entity-joined one. (`BlockDeviceSample` is 8 fields now — the instance's `block` AE row still fits 2 drives per page.)

A device whose diskstats row is missing this tick reports `null` rates for that tick but **keeps its baseline**. v4 invalidated here, which cost two ticks of nulls for one bad read — the tick itself, then the re-origin tick — i.e. a two-minute hole at the 60 s cadence from a single transient failure. `CounterBaselineTracker.delta` already detects the two cases where a baseline is genuinely invalid (counter went backwards, or the host rebooted), so carrying it across a missing read is safe.

**Traffic adapters** (`collector/ingress/` + `collector/router/` + `collector/database-proxy/`): three independent domains, one adapter each. `ingress/caddy.ts` (site Caddy — `orchestration/roles/site-caddy`, **not** the hosting Caddy in `src/deploy/ingress.ts` — reachable at `SITE_CADDY_ADMIN_ADDR`, `127.0.0.1:2039`; that role's `Caddyfile.j2` sets the global `metrics` option, which exposes the result at `/metrics` on its own admin listener) feeds `ingressSources[]`. `router/traefik.ts` (the shared hosting-ingress Traefik — `src/deploy/ingress.ts`'s loopback-only `TRAEFIK_METRICS_ADDR` Prometheus entrypoint, **not** any per-service tenant Traefik) feeds the host-wide singleton `router` field. `database-proxy/proxysql.ts` (managed ProxySQL — `src/managed/proxysql.ts` — `admin-restapi_enabled`/`admin-restapi_port` start an unauthenticated `GET /metrics` REST server, published to `PROXYSQL_REST_ADDR`, `127.0.0.1:6070`, only) feeds `databaseProxies[]`.

**Why Traefik is not an ingress source.** v5 reported it as a second `ingressSources[]` entry alongside Caddy, which forced both vendors onto one 17-field layout that fit neither: Traefik's `traefik_service_*`/`traefik_router_*` view (backends, services, retries, config reloads, TLS expiry) has no Caddy analogue, and Caddy's per-handler request accounting has none in Traefik. v6 split it into `managed.router` — host-wide and singleton (a host runs exactly one shared router, so there is no `sourceId`), the same shape family as `diagnostics`. `RouterReadContext` carries `nowMs` for the two clock-relative fields (`configLastReloadAgeSeconds` and `tlsCertSoonestExpiryDays` are read off Unix-timestamp gauges). `src/deploy/ingress.ts` must keep passing `--metrics.prometheus.addRoutersLabels=true`: Traefik defaults it off, and without it `traefik_router_*` never appears and `routersTotal` is permanently `null`.

Each adapter's presence is scrape-derived, not topology-enumerated — there is no fixed entity list the way GPUs/NICs have one — so `ingress/index.ts`'s `buildIngressSources`, `router/index.ts`'s `buildRouterSample` and `database-proxy/index.ts`'s `buildDatabaseProxies` each read their adapter every tick and an absent/unreachable one is simply omitted (an empty array, or the `router` key absent from the sample entirely — never an all-`null` placeholder) with its `CounterBaselineTracker` key namespace invalidated so a later readable tick re-origins instead of diffing across the gap. Counter fields are shipped as raw **per-interval deltas** via `CounterBaselineTracker.delta` (never divided by the interval — the instance's `delta-sum` aggregation sums them into a window total); first-sample, counter-decrease (sidecar restart), and boot-generation-change all null the field and re-baseline — the full battery (reboot, counter wrap, sidecar restart, device replacement) is regression-tested end to end in `collector/baseline-reset-battery.test.ts`.

**Latency is shipped as a sum plus buckets, never an average or a percentile.** `caddy.ts` emits `requestDurationSecondsSum` undivided and six cumulative-`le` bucket counters (`bucket10ms`..`bucket5s`, matching Caddy's default histogram bounds); the instance derives the mean and p50/p90/p99 at read time. v5 shipped a pre-divided average, which could not be re-aggregated across windows. `src/deploy/ingress.ts`'s `--metrics.prometheus.buckets` was widened to `0.01,0.05,0.1,0.5,1.0,5.0` for the same reason — the old four-bound set bottomed out at 100ms, which put every request on a healthy site in the first bucket. ProxySQL gets means but no percentiles: its catalog has cumulative time counters (`proxysql_backend_query_time_seconds_total`, `proxysql_query_processor_time_seconds_total`) and no histogram to derive them from.

Caddy's `caddy_http_requests_total` counter and its per-handler duration histogram can disagree when a route is nested/re-instrumented; `caddy.ts` resolves each server's outermost handler group as the sole authoritative aggregation scope rather than summing every group (see that module's doc comment for the full rule). `requestErrors` stays `null` on Caddy (no per-request error counter distinct from the 5xx response class) and so does its `retries` (no Caddy equivalent to `traefik_service_retries_total`) — both are left `null` rather than approximated from an unrelated metric. Every adapter shares `collector/proxy/prom-exposition.ts`'s Prometheus text parser and `collector/proxy/endpoint-cache.ts`'s retry-bounded probe wrapper (`PROXY_ENDPOINT_RETRY_MS` = 5 min, mirroring `DOCKER_DATA_ROOT_RETRY_MS`, so a stopped sidecar is not re-dialed every tick forever — unlike the Docker data-root cache, a *successful* scrape is never remembered; traffic counters must be re-read every interval).

**Host storage accounting** (`storage?` / `dockerUsage?`): two host-wide singleton families, both fed from **cached** readings the sample tick only reads — never computes. `collector/directory-usage.ts` owns a `DirectoryUsageWalker` on its own `DIRECTORY_USAGE_WALK_INTERVAL_MS` (15 min) timer covering the hosting root, the backup root (`LayoutPaths.backupDir` — `/backup` by default, `TURBOPANEL_BACKUP_DIR` to override) and the log directory (`LayoutPaths.logDir`); `collector/docker-usage.ts` owns a `DockerUsageSampler` polling Docker's `GET /system/df` every `DOCKER_USAGE_REFRESH_INTERVAL_MS` (5 min) through `DockerClient.systemDf`. Both are module-level singletons constructed and started by `collector/index.ts`'s `defaultDeps()` and stopped by `stopHostStorageSamplers()` on daemon shutdown (`daemon-run.ts`); they survive a control-plane reconnect because what they measure is a property of the host, not of the connection. `CollectorDeps.directoryUsage` / `.dockerUsage` are **getters**, not probes, precisely so nothing puts a recursive tree walk or a `/system/df` scan on the 60 s path.

A path that is its own mount point is read straight from `statfs` (`(blocks - bfree) * bsize`), never walked — the common shape for `/backup` on attached storage. Only a directory sharing a filesystem with others is walked, and the walk is bounded three ways (`DIRECTORY_USAGE_MAX_DEPTH`, `DIRECTORY_USAGE_MAX_ENTRIES`, plus an event-loop yield every `DIRECTORY_USAGE_YIELD_EVERY` entries). Hitting a bound, or an unreadable subdirectory, reports `null` rather than a partial total: an under-count rendered as a real number silently understates a filling disk, which is the one thing this metric exists to catch. Symlinks are counted by their own size and never traversed. `sample.storage` stays absent entirely until the first walk completes, so a freshly started daemon reports no storage row rather than a row of zeros; `sample.dockerUsage` stays absent whenever the Docker socket is unreachable (same discipline as `DockerClient.ping()`). `storage.dockerUsedBytes` is the Docker breakdown's own total (layers + container writable layers + volumes + build cache), `null` when any component is unknown. `reduceDockerSystemDf` reads layer bytes from the Engine's `LayersSize` — the deduplicated total — never by summing `Images[].Size`, which counts every shared base layer once per image.

The twelve per-engine census fields on `StorageSample` (`postgres`/`mysql`/`mariadb` × instances running/healthy, connections used/max) come from a third slow-timer singleton, the **managed-engine census** (`collector/managed-engines.ts`'s `ManagedEngineSampler`, every 5 minutes): one `GET /containers/json?all=true` over the Docker socket finds every container stamped `tp.managed.engine=<code>` (`managed/compose.ts`'s `MANAGED_ENGINE_LABEL` — discovery is by label, never by image name), `instancesRunning` counts Docker's `running` state, and each running instance is asked `ManagedEngineRuntime.readCensus` (`managed/engines/*.ts` — the readiness probe `waitReady` polls, taken once, plus `Threads_connected`/`pg_stat_activity` against `max_connections`) through the same `docker exec` path the managed apply/lifecycle handlers use. That exec is a subprocess, which is why the census has its own timer (the `smart.ts` precedent) and the 60 s tick only reads the cached result. An engine with no container of its kind stays `null` (the console hides that engine's series); an engine with containers present reports real counts, including `0` running; `connectionsUsed`/`connectionsMax` are `null` for an instance whose probe passed but whose census query was refused (MySQL/MariaDB volumes without socket auth — this path carries no password).

**Filesystem roles** (`topology/types.ts`'s `FilesystemRole`): `root` / `hosting` / `docker` / `backup` / `logs` / `application` / `custom`. `backup` and `logs` were added in v6 alongside `managed.storage`; unlike the hosting path and the Docker data root, neither needs discovery — both are plain `LayoutPaths` fields, so `FilesystemTopologyDeps.resolveBackupPath` / `.resolveLogsPath` are synchronous string getters rather than probes that can fail. `slot-mapping.ts` pins **every** role-bearing filesystem ahead of the rest, in a fixed `FILESYSTEM_ROLE_PRIORITY` (`root`, `hosting`, `docker`, `backup`, `logs`), with an operator `hostingFilesystemId` override taking the very first slot; everything else follows sorted by id. That is what keeps the filesystems a storage panel renders on the first page as unrelated mounts come and go. `application`/`custom` are deliberately not pinned — they are operator labels with no fixed product meaning. The control plane mirrors this file verbatim at `turbopanel/src/client/servers/topology-slot-mapping.ts`; a divergence would let the two disagree about which filesystems are pinned.

**Diagnostics** (`diagnostics?`): one collector, `diagnostics.ts`'s `buildDiagnosticsSample`, produces both halves of the merged v6 depth family (v5 had two separate collectors behind two capability flags). The `cpu` half reports host-wide frequency/scheduling counters only (frequency min/avg/max, context switches, interrupts, forks/s, combined irq+softirq percent) — 7 scalars, no per-core breakdown. The `memory` half reports the slab/dirty/writeback/commit breakdown from `/proc/meminfo` (`parse-meminfo.ts`'s `parseMeminfoDiagnostics`) plus reclaim/compaction rates from `/proc/vmstat` — `pageScanDirectPerSecond`/`pageScanKswapdPerSecond` are kept separate rather than combined, since a direct-reclaim-heavy host is under acute memory pressure in a way a kswapd-heavy host is not.

The two halves degrade independently: a tick that can read `/proc/stat` but not `/proc/meminfo` still reports the CPU half with the memory half all-`null`, and only a tick where none of the three source files is readable drops the family entirely. v6 also dropped seven never-charted `/proc/meminfo` gauges v5 collected (`pageTablesBytes`, `kernelStackBytes`, `commitLimitBytes`, and the four `Active`/`Inactive` anon/file LRU gauges), which is what lets the merged 7 + 12 field set fit one 19-slot Analytics Engine row.

**Unsupported OS:** `UnsupportedMetricsCollector` returns `{ supported: false, reason: "unsupported_os:<os>" }` and keeps the daemon running.

**Env:** `TURBOPANEL_SERVER_METRICS_RETENTION_DAYS` default `90` (instance raw-metrics retention). Server metrics are always on — there is no instance-side enable/disable gate; the daemon always collects and emits host metrics fire-and-forget, and the instance always persists when a backend is configured.
